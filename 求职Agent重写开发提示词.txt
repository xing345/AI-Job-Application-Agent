============================================================
自动求职 Agent 重写开发提示词
============================================================

一、项目定位
============================================================

你是一个真正的 LLM-driven Agent，核心能力是：
自动发现岗位 → 标题语义初筛 → 抓取完整 JD → LLM 深度匹配
→ 用户确认投递清单 → 自动填写投递表单 → HITL 等待提交。

不是写死流程的爬虫脚本，每个关键决策环节都有大模型参与。

技术栈（硬约束）：
- Python 3.11+，所有 IO 和浏览器操作用 async/await
- Playwright（浏览器自动化）
- LangGraph（Agent 状态机 / 决策循环）
- 大模型 API（OpenAI 兼容接口，统一 llm_client 调用）
- Pydantic v2（所有数据模型）
- python-dotenv 管理密钥，禁止硬编码

明确不做的事：
- 不做简历修改 / 简历生成功能（全部删除）
- 不做邮件监听、日历同步、仪表盘、通知推送等外围功能
- 不做 Tavily 关键词搜索（岗位发现只走官方招聘网站分类导航+分页）
- 不自动点击最终「提交申请」按钮（必须 HITL 确认后用户手动点）
- 不绕过登录、验证码、人机验证（遇到就停，不猜不跳）


============================================================
二、Agent 架构（LangGraph 状态机）
============================================================

状态机节点流程：

[加载用户画像+简历]
    → [岗位发现：分类导航遍历+分页，全量收集岗位标题]
    → [标题语义初筛：LLM 批量判断哪些标题与目标方向相关]
    → [JD 详情抓取：只打开通过初筛的岗位，提取完整 JD]
    → [LLM 深度匹配：读完整 JD 对比简历，输出匹配报告]
    → [用户确认投递清单：配额感知排序，用户选岗]
    → [循环投递每个岗位]
        → [进入申请页]
        → [检测登录墙/验证码，HITL 暂停]
        → [表单字段发现：Playwright 元素级提取]
        → [LLM 字段语义理解+值生成（结合 JD 生成针对性回答）]
        → [执行填写+上传简历]
        → [HITL 等待用户手动提交]
        → [记录结果]
    → [下一个岗位或结束]

每个节点是 LangGraph StateGraph 的一个节点，通过共享 AgentState 传递数据。


============================================================
三、大模型运用的四个核心场景
============================================================

LLM 不是装饰，以下四个环节必须真实调用大模型，不能用规则代替：

1. 标题语义初筛
   - 批量判断岗位标题是否与目标方向语义相关
   - 一次调用处理 20 个标题，轻量高效
   - 过滤明显不相干的岗位（行政、财务、销售等）

2. JD 深度匹配
   - 读完整 JD（岗位职责+任职要求）+ 简历全文
   - 输出结构化匹配结果：分数、匹配点、缺失点、理由
   - 不看标题判断方向，看 JD 实际内容

3. 表单字段语义理解+值生成
   - 理解每个表单字段的语义（label 文本，不依赖 name 属性）
   - 从简历+用户画像提取对应值
   - 开放式问题（为什么加入我们、个人优势）结合 JD 生成针对性回答

4. 投递配额排序（可选触发）
   - 当候选岗位超过公司投递上限时，LLM 辅助排序推荐
   - 优先目标方向岗位，不足时用高匹配度岗位补足


============================================================
四、页面内容提取原则（关键）
============================================================

提取和语义理解分离：Playwright 做元素级结构化提取，LLM 只做语义判断。

禁止的做法：
- 禁止 page.content() 拿整页 HTML 截断后塞给 LLM
- 禁止让 LLM 从 HTML 中提取职位列表或表单字段
- 禁止用 3000 字符截断处理长页面

正确的做法：

岗位列表页：
- 用 CSS selector 遍历岗位卡片
- 提取标题、公司、地点、详情页 URL
- 输出 List[JobPosting]，不调 LLM

岗位详情页：
- 打开详情页，等待加载完成
- 提取完整 JD 文本（岗位职责+任职要求），不截断
- 输出 JobDetail，不调 LLM

申请表单页：
- 用 Playwright 遍历所有 input/textarea/select/radio/checkbox
- 提取每个元素的 label、placeholder、name、type、options
- 组装成结构化字段列表
- 再把字段列表传给 LLM 做语义映射和值生成


============================================================
五、三层岗位筛选机制（核心设计）
============================================================

第一层：标题语义初筛（轻量，批量 LLM）
- 列表页全量收集所有岗位标题（Playwright 提取，不调 LLM）
- 每 20 个标题打包，一次 LLM 调用判断语义相关性
- Prompt 要点：
  * 不要求标题字面一致，意思相关就算
  * 例：目标"AI Agent开发"，则"大模型应用工程师"、"LLM开发"、
    "智能体研发"、"对话系统工程师"、"RAG工程师"都算相关
  * 明显不相干的（行政、财务、销售、HR、文案）排除
  * 拿不准的算相关，进入下一层用 JD 判断，不误杀
- 输出：related_indices / unrelated_indices
- 成本：100 个岗位只需 5 次 LLM 调用，过滤掉 70%-80%

第二层：详情页抓取（只对通过初筛的岗位）
- 打开详情页，提取完整 JD（不调 LLM）
- 遇到登录墙/验证码 → HITL 暂停

第三层：JD 深度匹配（逐个 LLM）
- 对完整 JD 做详细匹配评估
- 输出匹配度分数、匹配点、缺失点
- 调用次数 = 通过初筛的岗位数（通常 20%-30%）


============================================================
六、投递配额感知机制
============================================================

站点配置：
- 每个招聘站点配置 max_applications_per_cycle（如 3）
- 配置 cycle_days（配额重置周期，如 30 天）
- SQLite 记录每个公司已投递岗位和时间，自动去重

触发条件：
- 候选岗位数 > 该站点配额上限时，触发 LLM 排序

LLM 排序 Prompt 要点：
- 输入：候选人目标方向 + 简历摘要 + 候选岗位列表（含匹配度和 JD 摘要）
- 决策规则：
  1. 优先选择与目标方向一致的岗位（即使匹配度略低）
  2. 目标方向岗位不足时，用高匹配度岗位补足
  3. 考虑岗位多样性，不全选同一类
  4. 每个选择给出理由
- 输出：recommended（岗位序号列表）+ reasoning（选择理由）

用户确认：
- 终端展示推荐列表 + 被排除岗位 + 排除原因
- 用户可接受推荐，也可手动调整


============================================================
七、HITL（人在回路）机制
============================================================

触发场景：
- 登录墙（密码框 + 登录语义标题/表单）
- 验证码（reCAPTCHA、滑块、图形、短信验证码）
- 403 / 人机验证页面
- 表单无法识别 / 无法生成填写指令
- 最终提交按钮（永远等用户手动点）

实现要求：
- pause() 必须真正阻塞 asyncio 任务，不能用 time.sleep 或跳过
- 暂停期间浏览器保持打开，用户可手动操作
- 终端打印醒目的暂停提示（原因 + 当前 URL）
- 等待用户在终端输入 continue 后恢复
- 恢复时重新读取当前页面 URL 和标题，确认状态
- 暂停期间不运行任何自动化操作

检测方式：
- 登录墙：可见密码输入框 + 登录语义标题/表单 action/按钮
- 验证码：.g-recaptcha、iframe[src*=captcha]、
  input[name*=captcha]、页面文本含"验证码/图形验证/滑块验证"
- 每个浏览器操作前先检测，命中立即暂停


============================================================
八、自动填写投递表单（核心功能）
============================================================

对每个确认投递的岗位执行：

1. 进入申请页
   - 点击「立即投递」/「申请职位」按钮
   - 检测登录墙，需要登录则 HITL 暂停

2. 表单字段发现
   - Playwright 提取所有可填写元素
   - 每个元素获取：关联 label 文本、placeholder、name、type、options
   - 组装结构化字段列表，不调 LLM

3. LLM 字段语义理解+值生成
   - 输入：字段列表 + 用户简历 + 用户画像 + 岗位 JD
   - LLM 输出每个字段的：语义分类 + 填写值
   - 开放式问题结合 JD 生成针对性回答，不用通用模板
   - 不确定的字段填 null，不编造
   - 用 Pydantic structured output 约束返回格式

4. 执行填写
   - 文本框 fill()，下拉 select_option()，单选/复选 click()
   - 每个字段填写后验证值是否正确写入
   - SPA 框架 fill 后额外 dispatch input/change 事件
   - 失败字段记录，最后汇总给用户
   - 文件上传字段自动上传 resume.pdf

5. 暂停等待提交
   - 所有字段填完后，不点击提交按钮
   - HITL 暂停："表单已填写完毕，请检查并手动点击提交"
   - 用户检查后手动提交，输入 continue 恢复

6. 记录结果
   - 每个岗位投递状态（成功/失败/失败原因）写入 SQLite


============================================================
九、数据模型
============================================================

UserProfile：
- 姓名、电话、邮箱
- 教育背景（学校/专业/学历/起止时间）
- 工作/实习经历（公司/职位/时间/职责/成果）
- 项目经历（名称/角色/技术栈/描述/成果）
- 技能列表
- 目标城市、目标岗位方向、期望薪资、可到岗时间
- 个人简介

Resume：
- 结构化简历数据，从 PDF 或 JSON 加载，只解析不修改

JobPosting（列表页信息）：
- 标题、公司、地点、详情页 URL、分类路径

JobDetail（详情页信息）：
- 完整 JD 文本、岗位职责、任职要求、薪资、地点、发布时间、申请入口 URL

MatchResult：
- 岗位引用、匹配度分数（0-100）、方向匹配（bool+理由）、
  匹配点列表、缺失点列表、LLM 生成的匹配理由

FillField：
- 字段 label、语义类型、填写值、填写状态（pending/filled/failed）

AgentState（LangGraph 共享状态）：
- profile、resume、discovered_jobs、job_details、
  match_results、apply_queue、current_job_index、
  fill_results、errors

============================================================
十一、LLM 客户端规范
============================================================

- 异步调用，OpenAI 兼容接口（base_url + api_key 从 .env 读）
- temperature = 0.1（任务型，减少幻觉）
- 统一方法：async def chat(messages, response_format=None) -> str
- 支持 Pydantic structured output（用 model_json_schema 约束）
- 指数退避重试 3 次，超时 30 秒
- 每次调用记录日志（prompt 摘要 + token 用量）
- 所有 prompt 集中在 llm/prompts.py，不散落各模块


============================================================
十二、开发步骤（按顺序，每步可独立验证）
============================================================

Step 1：数据模型与 LLM 客户端
- 定义所有 Pydantic 模型
- 实现 llm/client.py，验证 structured output 可用
- 验收：调用 LLM 把自然语言转成 UserProfile JSON

Step 2：浏览器管理与 HITL 机制
- browser/manager.py：持久化 profile，headless=False
- browser/hitl.py：BlockHandler.pause() 真正阻塞
- 验收：打开登录页，检测到后暂停，用户登录后输入 continue 恢复

Step 3：岗位发现（分类导航+分页）
- search/site_registry.py：配置至少 3 个招聘站点
- search/discoverer.py：遍历分类+分页，全量收集 JobPosting
- 去重（按 URL），断点续跑
- 验收：输出某站点全部分类下的全部岗位，数量与网站实际一致

Step 4：标题语义初筛
- agent/nodes/screen_titles.py
- 每 20 个标题批量调用 LLM 判断语义相关性
- 验收：100 个混合岗位（含相干和不相干），验证过滤准确率

Step 5：JD 详情抓取
- agent/nodes/fetch_jd.py
- 只打开通过初筛的岗位，提取完整 JD
- 验收：5 个岗位，验证提取出完整 JD 文本（非片段）

Step 6：LLM 深度匹配
- agent/nodes/match_jobs.py
- 读完整 JD + 简历，输出 MatchResult
- 按分数降序，输出匹配报告 JSON
- 验收：3 个真实岗位 + 真实简历，人工核对匹配度合理性

Step 7：用户确认投递清单（含配额排序）
- agent/nodes/confirm_list.py
- 终端展示匹配表格，用户选岗
- 超过配额时触发 LLM 排序推荐
- 支持直接输入岗位 URL 跳过发现/匹配
- 验收：展示表格，用户输入编号后正确筛选投递队列

Step 8：自动填写投递表单
- agent/nodes/fill_application.py
- 字段发现（Playwright）→ LLM 语义映射+值生成 → 执行填写 → 上传简历 → HITL 等待
- 验收：1 个真实岗位，验证字段发现正确、LLM 映射正确、
  填写后页面值正确、最终停在提交前等待

Step 9：LangGraph 编排与主入口
- agent/graph.py：StateGraph 节点+条件边+循环
- main.py：命令行参数（--resume, --profile, --job-url, --site）
- 验收：完整跑通从发现到投递的流程

Step 10：错误处理与日志
- 每个节点 try/except，异常写入 AgentState.errors
- 日志格式：[时间] [节点名] [级别] 消息
- 浏览器失败截图保存
- 断点续跑：状态持久化到 SQLite，--resume 恢复

============================================================
十四、关键设计原则（开发时反复对照）
============================================================

1. LLM 不是装饰：标题初筛、JD匹配、字段理解、配额排序这四个环节
   必须真实调用大模型，不能用规则或关键词代替。

2. 提取与语义分离：Playwright 做元素提取，LLM 做语义判断。
   禁止给 LLM 喂整页 HTML。

3. 三层漏斗：标题语义初筛（批量轻量）→ 详情页抓取 → JD深度匹配。
   越往后调用越少、越重。

4. 标题语义匹配：不要求字面一致，意思相关就算。
   拿不准的算相关，不误杀。

5. 匹配看完整 JD：必须打开详情页，不能只看标题或搜索片段。

6. 填表靠语义不靠 name：LLM 看 label 文本判断字段含义，
   不依赖硬编码的 name 属性映射。

7. 开放式问题结合 JD：回答必须对应 JD 中的具体要求，不用通用模板。

8. HITL 是硬中断：pause() 真正阻塞，暂停期间不运行任何自动化。

9. 绝不自动提交：最终提交按钮永远等用户手动点。

10. 投递配额感知：超过公司上限时 LLM 排序推荐，用户最终确认。
